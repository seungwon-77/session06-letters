# 익명 고민 편지함 — 발표용 구조·설계 설명

## 1. 한 줄 소개
고민을 익명으로 게시하면, 누구나 마음 가는 고민에 댓글로 답장을 남기는 서비스.
로그인 없이 바로 쓰고 바로 답할 수 있게 만들었다.

## 2. 사용자 흐름 (하나의 흐름을 끝까지)
```
홈(고민 목록) ─┬─ 고민 부치기(/write) → 저장 → 내 고민 글(/letter/[id])로 이동
              └─ 고민 클릭 → 고민 본문 + 답장 목록(/letter/[id]) → 댓글로 답장
```

## 3. 전체 구조 — 3개 층
```
[사용자 브라우저]
   │  ① Vercel에서 화면(HTML·JS) 받아옴
   ▼
[Next.js 앱]  ← Vercel이 배포·호스팅
   │  ② Supabase SDK로 데이터 요청 (HTTPS)
   ▼
[Supabase]  Data API → 권한·RLS 검사 → PostgreSQL (letters, comments)
```
- **Vercel**: 화면 코드를 전 세계에 배포. GitHub에 push하면 자동 재배포.
- **Next.js**: 화면 4개. 데이터는 브라우저에서 Supabase로 직접 요청.
- **Supabase**: DB + 자동 생성 API + 권한 관리. 별도 백엔드 서버를 만들지 않았다.

**왜 백엔드 서버가 없나?** Supabase가 테이블마다 API를 자동으로 만들어 주고, "누가 무엇을 할 수 있나"를 DB 권한(RLS)으로 막을 수 있어서 MVP에서는 서버가 하는 일이 없다. 코드가 줄고 배포 대상도 하나로 줄어든다.

## 4. 요청 하나 따라가기 — "고민 부치기" 버튼
1. 브라우저: 입력값 앞뒤 공백 제거, 1000자 넘으면 버튼 비활성화 (1차 검사)
2. SDK: `letters` 테이블에 `{content}` insert 요청 + 새 글 id 돌려받기
3. Supabase: anon 권한에 insert가 허용됐는지 → RLS 정책 통과? → 제약조건(1~1000자, 공백만 X) 검사 (2차 검사)
4. DB가 id(uuid)와 작성시각을 자동 생성해 저장
5. 브라우저: 받은 id를 localStorage에 "내 글"로 기억 → `/letter/{id}`로 이동

검사를 두 번 하는 이유: 화면 검사는 사용자 편의용, DB 검사는 진짜 방어선. 화면 검사는 개발자도구로 우회 가능하다.

## 5. DB 설계
| 테이블 | 컬럼 | 제약 |
|---|---|---|
| `letters` (고민) | id(uuid), content, created_at | 1~1000자, 공백만 불가 |
| `comments` (답장) | id, **letter_id → letters.id**, content, created_at | 1~500자, 공백만 불가 |

- **1:N 관계**: 고민 1개에 답장 여러 개. 답장 테이블이 `letter_id`로 고민을 가리킨다(외래키).
- **외래키 효과**: 없는 고민에 댓글 다는 요청은 DB가 거부. 고민이 지워지면 댓글도 같이 지워짐(`on delete cascade`).
- **id를 uuid로**: 1,2,3 같은 순번이면 URL을 바꿔 가며 전체 글을 훑기 쉽다. uuid는 추측이 어렵다.
- **인덱스 2개**: 목록(최신순 50개)과 고민별 댓글 조회가 데이터가 늘어도 빠르게.
- **목록의 "답장 N통"**: 고민 목록 조회 한 번에 `comments(count)`로 댓글 수까지 같이 가져온다. 고민마다 따로 세면 요청이 50번 더 나간다.

## 6. 보안 설계 — 공개 키인데 왜 안전한가
브라우저 코드에 Supabase **publishable key**가 들어 있다. 누구나 볼 수 있는 키다.
그래서 "키를 숨기는 것"이 아니라 "**키로 할 수 있는 일을 DB가 제한**"하는 방식이다.

| 동작 | 허용? | 어떻게 막나 |
|---|---|---|
| 고민·댓글 읽기 | ✅ | select 권한 + RLS 정책 |
| 고민·댓글 쓰기 | ✅ (내용만) | **컬럼 단위 권한**: content, letter_id만 넣을 수 있음 |
| id·작성시각 조작 | ❌ | 해당 컬럼에 insert 권한 없음 |
| 수정·삭제 | ❌ | update/delete 권한·정책 자체가 없음 |

실제로 확인함: 공백 글 → 제약조건 거부 / id 지정 → 권한 거부 / 없는 글에 댓글 → 외래키 거부 / 수정·삭제 → 401.

## 7. 화면(라우트) 설계
| 경로 | 역할 |
|---|---|
| `/` | 고민 목록 + 답장 수 + "고민 부치기" 버튼 |
| `/write` | 고민 작성 폼 |
| `/letter/[id]` | 동적 라우트. 주소의 id로 고민 + 댓글을 불러옴 |

- 공통 헤더·푸터는 `layout.tsx` 하나로.
- 저장 중엔 버튼 잠금(중복 제출 방지), 실패 시 입력 유지, 로딩/빈 목록/에러 상태 모두 화면에 표시.
- 지연된 이전 요청이 최신 결과를 덮어쓰지 않도록 요청 번호로 확인.

## 8. 익명성과 "내 고민" 표시
- 로그인이 없으니 서버는 글쓴이를 모른다 → **진짜 익명**.
- 대신 내가 쓴 글 id를 **브라우저 localStorage**에 저장해서 목록에 "내 고민"으로 표시.
- 트레이드오프: 다른 기기·시크릿 창에서는 "내 고민" 표시가 사라진다. 익명성을 위해 감수한 부분.

## 9. 설계하며 바꾼 결정
- 처음엔 "무작위로 고민 하나를 받아 답장"하는 구조였다 → **게시판형으로 변경**.
  이유: 사용자가 공감 가는 고민을 직접 골라 답하는 게 더 자연스럽고, 다른 사람의 답장도 함께 볼 수 있어서 위로가 쌓인다. 무작위 뽑기용 DB 함수가 없어져 구조도 더 단순해졌다.
- 답장 수 제한 없음: 한 고민에 여러 관점의 답이 쌓이는 게 이 서비스의 가치.

## 10. 한계와 다음 단계
| 한계 | 다음 단계 |
|---|---|
| 신고·삭제 기능 없음 (악성 글 대응 X) | 신고 버튼 + 관리자 숨김 처리 |
| 도배 방지 없음 | 요청 횟수 제한(rate limit), 캡차 |
| 목록 최신 50개까지만 | 페이지네이션 / 무한 스크롤 |
| "내 고민"이 기기에 묶임 | Supabase 익명 로그인으로 기기 간 유지 |
| 새 댓글은 새로고침해야 보임 | Supabase Realtime으로 실시간 반영 |
| 내 고민에 답장이 와도 모름 | 알림(이메일·푸시) |

## 11. 예상 질문과 답
- **Q. 키가 공개돼 있는데 해킹 안 되나요?** → 키는 원래 공개용. 권한은 DB의 RLS·컬럼 권한이 막는다. 수정·삭제 요청을 직접 보내 봤고 401로 막혔다.
- **Q. 서버 없이 괜찮나요?** → 이 MVP에서 서버가 하는 일(저장·조회·권한 검사)을 Supabase가 다 한다. 신고 처리나 알림처럼 서버 로직이 필요해지면 Next.js의 Route Handler나 Supabase Edge Function을 추가하면 된다.
- **Q. 왜 로그인을 안 넣었나요?** → 고민 서비스는 "이름이 남지 않는다"는 게 진입장벽을 낮추는 핵심. 로그인 대신 localStorage로 최소한의 "내 글" 표시만.
- **Q. 악성 댓글은요?** → 현재 한계. 다음 단계에서 신고 + 숨김 처리.
- **Q. 고민 글과 댓글을 왜 테이블 두 개로 나눴나요?** → 고민 1개에 댓글이 여러 개(1:N). 한 테이블에 넣으면 댓글 수만큼 고민 내용이 중복되거나 배열로 관리해야 해서 검색·제약조건이 어려워진다.
